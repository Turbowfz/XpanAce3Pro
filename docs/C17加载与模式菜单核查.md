# C17 相机共享库与菜单初始化核查

## 核查范围

2026-11-14，连接 PJX110，相机 `7.013.51`。设备只读，没有安装、强停、重启或停用其他模块。原件和运行诊断留 `_tmp`，不随源码公开。

## 共享库资格

### 真实诊断格式

本机 `dumpsys package com.oplus.camera` 的共享库部分是多行：

```text
    usesLibraryFiles:
      /system/framework/org.apache.http.legacy.jar
      /product/framework/com.oplus.camera.unit.sdk.jar
      /system_ext/framework/androidx.window.extensions.jar
      /system_ext/framework/androidx.window.sidecar.jar
      libcdsprpc.so
      libOpenCL.so
    timeStamp=...
```

这里直接列出了 unit SDK，**没有 adapter JAR**。不能把不存在的 adapter 直接声明当成资格要求，也不能把系统 `libraries` 注册表当成运行中已加载证据。

### 执行链证据

- 应用 `CameraUnitClientAdapter` 直接构造 `CameraUnitImpl`。
- `CameraUnitImpl.initialize` 的任务直接构造 unit SDK 的 `ConsumerImpl`。
- `CameraUnitImpl.openCamera` 直接构造 unit SDK 的 `ProducerImpl`。
- 原 unit SDK 已包含这些类；unit 与 adapter 中均有 APSClient。
- 本机共享库 XML 将 unit、兼容名称和 adapter 分别注册，没有 unit→adapter 依赖声明。

因此资格门要求真实直接 unit SDK 路径与哈希；adapter 直接列出时必须同目录。未直接列出 adapter 时，仅核对 unit 同目录下的 adapter 原厂哈希作为**配套内容一致性检查**，不声称它已被相机加载。

### 为什么不能简单允许 C16 SDK

继续按原 C16 实现核对，C17 XPAN 钩子所用出流、SurfaceWrapper、takePicture 等核心 SDK 描述符确实有一致部分，protobuf 配置描述符也相同。但应用桥接增加了真实行为：

- C17 `takePictureTouchDownStage2(int)` 的 0 表示执行拍摄，1 表示调用 `cancelTouchDownCapture()` 取消；C16 仅有无参拍摄方法，没有对应的 consumer 取消接口。
- 将所有参数转给旧无参方法会把取消变成拍照；忽略非零参数也不能伪装完整取消。
- C17 的运行输入内存查询还有新增未捕获的接口，不能猜 0 或只删除报错项。

因此 v2.0 仍应按本机原厂 C17 SDK 适配，不为通过检查而接受混搭；这些接口差异不是“有官方源码就能直接补任意库”的证明。

## XPAN 菜单与原数据库

相机入口工厂和数据库是两道门：仅启用 `com.oplus.feature.xpan.mode.support` 不保证已有数据库出现 XPAN。

原数据库：`mode_data.db`；表：`mode_info`。

```sql
mode_name varchar primary key,
mode_id integer,
position varchar,
rank integer,
support_edit boolean,
support_front boolean
```

C17 `mp.h`（DataBaseOperator）与 `mp.j`（ModeDataSQLiteOpenHelper）的原生 panel merge 会：

1. 根据 XPAN support 创建候选 `xpan`，id 28、panel 位置、后摄。
2. 在 headline 与 panel 两份现有列表中找同名项，已有则不插入。
3. 没有时使用现有 panel 最大 rank + 1，保留其他模式的位置和顺序。

但配置变化本身不是该 merge 的通用触发器。初始化还受应用构建指纹、已插入标记、数据库版本与初始化缓存影响。

### 不采用的办法

- 不删数据库或清相机数据。
- 不伪造 reset-setting 标记。
- 不提高或降低数据库版本来绕初始化：大升级和降级存在 drop table 路径，小升级也不是独立可靠触发条件。
- 不以 `void` merge 返回就宣称写入成功；原实现存在内部捕获异常。

后续如需要一次性迁移，优先核实原生 merge 的精确 ABI、已有排序完整快照、写入后验证及 UI 列表刷新。必要的设备数据库变更仍须单独许可；本次只确认源代码路径，没有新增或执行数据库操作。
