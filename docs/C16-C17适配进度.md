### 保存前 XDR 的实效缺口

当前路线只在原相机保存前改完整的内存 HEIC 数组，不再尝试猜最终文件安静时间后改写原图。要验证 C17 实际生效，必须取得原保存缓冲的 `PATCHED`／`ALREADY_SUFFICIENT` 证据，并核验最终新照片的 `tmap`／关联 XMP 上限至少 8，其他内容保持。

若本机走 HardwareBuffer，或 `tmap` 在后续 native 阶段才生成，则当前路径明确未覆盖。不能把接口注册成功、解析通过或 `NO_TMAP` 记录当作 XDR 8× 已完成，也不能退回不安全的文件截断写回。

继续静态核对已确认：APS 回调把 `ultrahdrGainMapBuffer`、`ultrahdrGainMapInfo` 作为不透明 `byte[]` 传入扩展数据；`gn.r.Q` 在原图写出及条件 EXIF 后交给文件扩展包装（部分 APS 自带扩展分支会跳过）。HardwareBuffer 写出函数 `FormatConverter.writeHardwareBufferToFile(buffer, fd, size)` 的 int 是 detached FD，long 是 APS 数据长度，不是倍率或时间戳。**现有证据没有给出 gainmap-info 的成员布局，也没有证明它如何生成 HEIF `tmap`，因此本轮不猜偏移、不清空 HardwareBuffer 强行换路线。** 保存返回也不是所有扩展写入完成证明。
