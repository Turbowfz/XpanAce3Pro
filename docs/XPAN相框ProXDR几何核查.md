## 样张与方法

用户提供 `IMG20261114143811.heic`，原始 SHA-256：

`49c3365b2ace06fcb316a147ff14d8ddb01fcf05b9e19d2316780fe0db3dd76c`

大小 3,720,203 字节。只操作项目 `_tmp` 内副本，原 HEIC 未改写。

- 独立读取 BMFF item、grid、属性及 `dimg/cdsc` 引用。
- 使用本机 libheif 1.23.4 与对应公开 C 头文件，按 item ID 解码主图与 gain-map；未将 gain-map 的缺失 aux 列表当成不存在。
- 解码输出仅供像素／几何核查，不是 Android ProXDR 显示效果验收。

## 不能归因于外层 65:24 尺寸

| 对象 | item | 外层尺寸 | 实际照片内容矩形 |
|---|---:|---|---|
| SDR 主图 | 10171 | 8504×5000 | x=156,y=988,width=8192,height=3024 |
| gain-map | 10217 | 4252×2500 | x=78,y=494,width=4096,height=1512 |
| tmap | 10000 | ispe=8504×5000 | dimg 依序指向主图、gain-map |

主图照片内容是 65:24；加上相框后外层不再是 65:24。gain-map 的外层、照片内容位置和尺寸均恰好减半，**照片 ROI 完全对齐**。

因此，不应直接把 HEIC `ispe`、EXIF 或整个 gain-map 强改成 8192×3024／65:24。外层包含相框，改尺寸会破坏真实画面。

## 已确认的相框异常

主图相框白区大部分 RGB≈255，但 gain-map 中出现两种明显不同的区域：

- 左右外边及上下部分白框：gain 接近 0。
- x=78..4173、上框 y≈200..493 与下框的一部分：gain 大量为 174。
- gain-map 上方 XPAN 标志的起始部分被裁切，下方文字也被画布边界截断；不是主图文字本身缺失。

在排除照片内容区后，取主图减半后仍近白的相框像素：

- 白框样本 4,369,662。
- gain=174 占约 52.42%；gain>3 占约 52.64%。
- 另约 2,068,986 个白框样本 gain=0。

这构成真实的**相框非中性增益／内容域裁切**证据，而不是仅靠容器尺寸推测错位。

## 当前倍率补丁为何不能解决

原文件 tmap：log2 maximum=`4843037/2097152`≈2.309340，线性 maximum≈4.956563；关联 XMP 一致。

当前 `XdrRatioPatch.raiseRatioMax(input,8)` 可以在完整样张内存副本上成功改变 16 个字节，仅修改已核对的 tmap 上限和 XMP 数值：

- 不改变照片或 gain-map 像素。
- 不改变相框范围、位置或裁剪。
- 不改变 EXIF／ispe。

按 gamma=1、min/offset=0 的 metadata 公式，gain 样本 174 对应的 full-weight multiplier 约：

- 原 maximum：2.98×。
- maximum 改为 8×后：4.13×。

这是元数据公式推导，**不是实际 Android 解码／屏幕亮度测量**。它说明单纯提高上限可能扩大既有白框提亮的不均匀，不能称为相框适配修复。

## 已核对代码路径

C17 `WatermarkAppHelper` 存在真实 gain-map 水印合成：

- 原图先经主 watermark assemble，再调用 gain 合成。
- 无 overlay 时构造黑色 gain 画布并按缩放后的照片 offset 复制原 gain。
- 有 overlay 时复用相框 overlay、背景和元素参数进行 assemble；不是所有增益图都完全没有加框。
- crop helper 可以执行中心裁剪；本样张 logo 和底部文字的裁切应与实际 frame overlay 域／target-height 参数核对。

尚需确定相框路径的实际 holder 和 gain map 参数、主 frame 位图是否直接进入 gain renderer，以及原生 HEIF 编码端如何消费这些结果。不能只凭代码存在宣布本样张命中所有分支。

## 修复方向与边界

优先修水印合成前的 gain-frame 布局：

1. 从同一次主画布得到明确内容矩形和最终 canvas。
2. 按主图→gain-map 的精确缩放，将照片 gain 复制到对应 ROI，保留照片 gain 像素。
3. 相框／文字背景应使用经过元数据确认的中性 gain，不复用主图白色 overlay 值，也不由猜测颜色判定任意照片区域。
4. 不能用中心 crop 对相框 gain overlay 猜对齐，应显式对应主图相框空间。
5. 校验 JNI 复制结果、目标边界；未知布局和失败保持原流程，不截断原图、重写 HEIC 或关闭相框/ProXDR。

以上证据对应的第一阶段代码已实现为 `XpanGainMapFrame.java`：只在 C17 的原 XPAN 相框/Y8/stage3/已知无框增益源半比例路径，替换增益合成用的独立几何与素材参数；主图素材、主图缓冲区、原增益源与原生资源生命周期不由模块改写。它不自建或释放 AHardwareBuffer，也不对落盘 HEIC 进行重编码。

条件校验在替换前完成，缺格式、RGB、原 gain 已含框（例如4096×2088）、未知裁剪或尺寸组合均保持原流程。后置日志仅报告参数应用／原方法返回，不能当作最终像素验证。尚未取得本张拍摄的原 rawMap，故不能保证样张原路径在当前子集内，也不能称所有相框都已修复。

另已补 `XdrRatioPatch` 的 clap/旋转/镜像及 essential 属性验证。该 guard 防止对不一致的显式空间布局提高倍率，**不是**对本张相框增益像素的修复。

初步回归：相框参数组件 3 项／31 个独立 Java 场景通过，纯倍率／几何 guard 共 9,178,150 个检查通过；完整模块回归正在运行。用户原图保持同一 SHA-256。本轮没有安装新补丁、操作手机、重启或发布。
